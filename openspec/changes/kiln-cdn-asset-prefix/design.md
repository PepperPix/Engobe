## Context
See `proposal.md`. `SiteAssetCopier` always writes `assets/`, whereas `AssetPipeline` confuses the URL prefix with a filesystem path. `TemplateRenderer` treats absolute prefixes as relative paths, and `SharedRenderContext` exposes the raw value. Manifests/image indexes use canonical `/assets/` paths; rewrites replace exact strings, and link checking ignores HTTP(S). `DevServer` builds in development mode and resolves requests directly against the output. The Pagefind partial and search script already use `site.base_path`/`data-pagefind-module`.

Code inspection on 2026-10-21 confirmed additional gaps: `FeedGenerator.GenerateAtom` writes `ContentItem.HtmlContent` directly into XML, outside existing HTML/CSS rewrites. `ShortcodeProcessor` intentionally provides canonical plugin URLs before Markdown conversion. CSS files are hashed before their reference rewrites; `@import` strings and `srcset`/`poster` are not handled. The development server retains the output path and routing configuration from startup, while rebuilds read the site again.

## Goals / Non-Goals
**Goals:** A reversible mapping between local asset keys and public URLs for rendering, optimization, fingerprints, CSS, Atom content, and offline checks. Final stylesheet bytes determine the hash; every published owned asset reference on a supported reference surface must use the same file mapping.

**Non-Goals:** No CDN network access/upload, Pagefind relocation, or checking of foreign external links. No bundler, JavaScript import analysis, or rewriting of inline CSS/scripts or arbitrary strings. No expansion of image selection to `srcset`/`poster`, new responsive image variants, or new parameters on stable Core interfaces.

## Decisions
**Initial decisions dated 2026-10-19, confirmed on 2026-10-21:**

1. Physical output remains `<outputDir>/assets/`. For example, `https://cdn.example.com/v2/media/` denotes only the public base; the CDN must route to the content of `assets/`. Output under the CDN path component is rejected because it contradicts the copier and output-directory namespace separation.
2. Use a central resolver instead of duplicating URI/path logic: canonical key → file and public URL, and inversely public URL → local key. `site.asset_prefix` provides the effective base including the base path with a trailing slash; the theme migration notice is part of implementation. Preserve canonical `ContentItem.HtmlContent` and `IAssetReferenceIndexBuilder.Build(items)` for image selection; project `page.content` only during rendering. Pass the build mode through internal context without configuration mutation/global state.
3. A root-relative prefix receives the effective base path exactly once; an absolute HTTP(S) prefix never does. Evaluate `--base-url` first. Inverse mapping checks scheme/host/port and segment-accurate path boundaries, respects encoding/path case, and separates query/fragment from the file key. Do not use naive string-prefix checks.
4. Preserve existing phase boundaries but correct the faulty internal fingerprint order: image selection/copying/optimization, WebP mapping, minification, dependency-ordered fingerprints/reference rewrites, HTML minification, and link checking. Map canonical, local base-path, and owned CDN URLs; resolve relative CSS targets from the stylesheet and preserve query/fragment. Skip foreign external/data/anchor targets. Prefix application remains active without fingerprinting.
5. Every development build (`kiln build` and `kiln serve`) replaces only absolute CDN bases with `/assets/`; root-relative prefixes remain. Reason: CDN previews would show old uploaded files and undermine live reload. `DevServer` maps the effective local asset base, including the base path, to `assets/` without a remote proxy or weaker host/traversal checks. No new configuration option.
6. Pagefind remains in `pagefind/` with the site base path, including module/chunks/CSS. Only Kiln's own `static/js/kiln-search.js` uses the CDN prefix; its dynamic import continues to use `data-pagefind-module`. The search component, binary resolution, and indexer contracts remain unchanged.

**Additional decisions confirmed on 2026-10-21:**

7. **Bounded, structured reference surfaces:** Rewrite HTML from content, themes, and plugins, including shortcodes, only in `src`, `href`, `srcset`, and `poster`. Process `srcset` as a candidate list with descriptors and possible `data:` URLs, not by blind comma splitting. CSS includes `url()` and `@import` in both string and `url()` forms; preserve import conditions. Reuse existing parsers/dependencies; no new CDN/bundler library. Supporting only `src`/`href` or `url()` would be smaller but leave agreed HTML/CSS output inconsistent. Global string replacement is rejected because of example text and executable inline code.
8. **Preserve the canonical shortcode and image model:** `ShortcodeProcessor` and the public reference index continue to use `/assets/`; no additional site/mode dependency in their public calls. The same projection covers references in later HTML. New reference surfaces do not expand the existing image optimization/reference-index scope. Early mutation of `HtmlContent` is rejected because it would cause image selection, repeated builds, and Studio callers to diverge. Asset URLs assembled in inline code remain outside this contract.
9. **Dependency-ordered finalization:** After copying/WebP and asset minification, map owned CSS dependencies back to local keys through the resolver. Finalize leaf assets first; a stylesheet first receives its final target URLs and then the hash of its actual output bytes. This processes `@import` chains from inside out. The shared rename manifest combines WebP and fingerprints. Finalize HTML and Atom content with it afterward. Alphabetical file order or a second rewrite after the CSS hash is rejected because the filename would no longer represent the content. Without fingerprinting, projection to unhashed targets suffices, without topological hash computation.
10. **Cycles are fingerprint errors:** Check the resolved local dependency graph, including self-references. With fingerprinting enabled, a cycle produces a build error with the file chain, regardless of `build.linkCheck`. Neither silent skipping nor a warning fallback to unhashed cycle files is allowed. With fingerprinting disabled, there is no additional cycle error. A hash fixed point cannot be computed reliably; unhashed exceptions would silently weaken the cache-busting guarantee.
11. **Atom HTML receives final absolute asset URLs:** Open already generated Atom feeds with structured XML processing limited to their HTML content fields; their decoded HTML passes through the same attribute rewrite, then valid XML with correctly escaped HTML is written. No global XML string replacement or blanket rewriting of feed metadata or article links. Owned asset URLs are always absolute in feeds: CDN base or `Origin` plus effective local base, including the development fallback. Offline checking therefore also recognizes owned absolute site asset URLs. Leaving feeds unchanged before finalization is rejected because WebP/fingerprints replace the original files. Moving feed emission entirely after the pipeline would require additional feedback to link checking; shared final projection avoids this.
12. **Local namespaces without silent precedence:** Before file output, compare the effective asset namespace with generated pages from the content/virtual-page catalog and reserved search/live-reload routes using segment-accurate boundaries. A page at or within the asset namespace collides; a parent home/index page outside the namespace does not. Pagefind is reserved when search is enabled; the live-reload endpoint remains `/__kiln/livereload`. An absolute base with the site origin is checked as a local route in production; a different origin is not. Development checks the local fallback it actually uses. Both assets-win and pages-win behavior are rejected because build success would conceal unreachable output.
13. **Freeze routing while serve is running:** Retain the startup configuration for `assetPrefix` and the effective base path. Before every rebuild, load and validate current configuration and compare these values; on a difference, reject the rebuild before file output and report a restart request through the existing SSE error/overlay channel. The last successful output and its routes remain available; normal rebuilds are possible again after restoring startup configuration. A restart adopts the new base. Automatic routing replacement is rejected because of additional state/concurrency logic. No hot-reload guarantee is added for other server settings already fixed at startup.

This defines the shared asset-addressing contract. Existing base-path, shortcode, and API-compatibility boundaries remain; the template variable change is explicitly a behavior migration, not a public .NET signature change.

## Risks / Trade-offs
- [Effective rather than raw `site.asset_prefix`] → Provide a migration notice for themes with additional `site.base_path` composition; helper-based themes need no manual prefixing.
- [Incomplete rewrites] → Test the HTML/CSS/Atom/WebP/hash/suffix matrix and disabled fingerprinting; protect public API/shortcode callers and the canonical index.
- [CSS cycles become new build errors] → Report the file chain and document resolving the cycle or deliberately using `build.fingerprint: false`.
- [CSS/HTML parsers change foreign values] → Explicitly verify unchanged `data:` candidates, descriptors, import conditions, query/fragment, example text, and inline code.
- [Asset namespaces can hide existing pages] → Reject before file output; test neighboring paths and other origins as non-collisions.
- [Prefix changes during serve require a restart] → Retain existing output and provide a clear overlay message instead of silently stale routes; test automatic recovery after reverting the change.
- [Misconfigured CDN] → Offline checking validates only the build artifact, not reachability, CORS, or cache headers.

## Migration Plan
1. Deliver the change as a feature with explicitly documented **BREAKING** template semantics and newly rejected configurations; release communication must state the theme migration rather than treating it as an unnoticed patch. The release date is outside this change.
2. Update custom themes from `site.base_path + site.asset_prefix` to the already effective base, or preferably use asset helpers; do not add a second slash. `site.yaml` retains camelCase `assetPrefix`, with no `asset_prefix` alias.
3. Route the CDN deployment origin to the content of `<outputDir>/assets/` and publish HTML/feeds and their corresponding asset files together for each build. Pagefind remains site-local. No automatic upload or runtime network test by Kiln.
4. Restart `serve` for preview configuration changes. For fingerprint cycles, untangle CSS references or explicitly disable fingerprinting; do not expect a successful hashed build.
5. Roll back through the previous Kiln version and its matching complete build including assets; revert theme composition if necessary. No data migration or change to canonical source files is required.
